## 1. Введение

В рамках этапов 1–3 реализован базовый узел децентрализованной P2P-сети: TCP-транспорт с кадрированием, криптографическая идентичность (Ed25519), маршрутизация Kademlia (XOR, k-bucket), итеративный поиск (`FIND_NODE`), а также **распределённое хранение подписанных адресных записей (`STORE` / `FIND_VALUE`)** с репликацией и отказоустойчивостью.

В ходе работы были учтены и исправлены все замечания по этапам 1–2 (пул соединений, обработка тайм-аутов, строгая проверка успешности lookup, устойчивость к перезапуску, LRU-вытеснение).

## 3. Реализация этапа 3 (Хранение DHT)

### 3.1. Структура подписанной записи (NodeRecord)
Запись содержит: `node_id`, `identity_public_key`, `addresses`, `sequence_number`, `issued_at`, `expires_at`, `alias`, `signature`.

**Канонизация и подпись:**
Подпись Ed25519 вычисляется по детерминированному JSON без поля `signature`. При получении записи узел проверяет:
1. Совпадение `NodeID = SHA-256("p2p:identity:ed25519:v1:" || pubkey)`.
2. Валидность цифровой подписи.
3. Срок действия (`expires_at > now`).
4. Защиту от отката (`sequence_number` не меньше уже сохранённого).

**DHT-ключ:**
- Для `NodeID`: `SHA-256("node:" || NodeID)`.
- Для псевдонима (`alias`): `SHA-256("alias:" || normalize(alias))` (перевод в нижний регистр, trim).

### 3.2. Локальное хранилище
Реализовано в `internal/dht/storage.go`.
- Защищено `sync.RWMutex`.
- Фоновая горутина удаляет просроченные записи каждые 30 секунд.
- При сохранении отклоняет откат версии (`sequence_number < existing`).

### 3.3. Сетевые операции
- **`PutRecord`:** находит 3 ближайших к DHT-ключу узла (R=3) и отправляет им `STORE_REQUEST`. Операция успешна, если подтвердили хотя бы 2 из 3. Локально тоже сохраняет.
- **`GetRecord`:** итеративный поиск (как `FIND_NODE`), но отправляет `FIND_VALUE_REQUEST`. Если узел возвращает запись — поиск сразу завершается. Если нет — возвращаются ближайшие контакты, и поиск продолжается. Найденная запись кэшируется локально.
- **Republish:** узел периодически проверяет свои записи (где `NodeID == self`). Если осталось меньше половины TTL — переопубликовывает с `sequence_number + 1`.

### 3.4. CLI-интерфейс
Для ручной проверки добавлены флаги:
- `--put "alias"` — эфемерный узел поднимается на свободном порту, публикует запись и выходит.
- `--get "alias"` — эфемерный узел ищет запись по сети и выводит JSON.

## 4. Результаты испытаний (Этап 3)

**Стенд:** 5 узлов на `127.0.0.1` (порты 9101–9105).

### Сценарий 1: Публикация и поиск
1. `./bin/node --config .../node-05.yaml --put "tester"`
   - Лог: `"msg":"put record","replicas_attempted":3,"replicas_ok":3`
   - Вывод: `put ok: alias=tester key=44f0ba8a...`
2. `./bin/node --config .../node-02.yaml --get "tester"`
   - Лог: `"msg":"get record: found via network","peer":"099da29d","iter":1`
   - Вывод: JSON с `"alias": "tester"` и валидной подписью.

### Сценарий 2: Отказ хранителей (Failover)
1. Запись опубликована (лежит на 3 узлах).
2. Убиты процессы `node-04` и `node-05` (два потенциальных хранителя).
3. Новый эфемерный узел делает `--get "tester"`.
   - Лог: `"timeouts":3` (видит мёртвых соседей), `"msg":"get record: found via network","peer":"0bb14159","iter":1`.
   - **Результат:** JSON с `"alias": "tester"` успешно возвращён. Требование «поиск записи после отказа хранителя» выполнено.

## 6. План этапа 4

Архитектура готова к внедрению:
1. **Защищённая сессия (AKE):** X25519 + Ed25519 (подпись транскрипта) + HKDF-SHA256 + ChaCha20-Poly1305. Оборачивает `transport.Conn`.
2. **Туннели:** `TUNNEL_BUILD`, `TUNNEL_DATA` через 3 ретранслятора. Пул туннелей и автоматическое перестроение при отказе.
3. **Прикладные сообщения:** E2E-защита, `APP_MESSAGE`, `APP_ACK`, история доставки.
4. **Файлы (продвинутый уровень):** нарезка на блоки, ACK, проверка SHA-256.
