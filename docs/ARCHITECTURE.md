# Архитектура узла P2P-сети (этапы 1–2)

**Проект:** защищённая оверлейная сеть передачи данных на основе пиринговых протоколов  
**Этапы:** 1–2 (транспорт, кадрирование, идентичность, Kademlia DHT, bootstrap)  
**Язык реализации:** Go 1.22+  

---

## 1. Обзор

Узел — независимый логический экземпляр программы со своим `NodeID`,
TCP-портом, каталогом состояния, таблицей маршрутизации и журналом.
Несколько логических узлов могут работать в одном контейнере или на
одной машине — каждый со своим `NODE_STATE_DIR`.

Реализованный функционал этапов 1–2:

- обмен кадрами прикладного протокола поверх TCP;
- устойчивая криптографическая идентичность на Ed25519;
- ограниченная таблица маршрутизации Kademlia;
- RPC `PING` и `FIND_NODE`;
- присоединение к сети через bootstrap-узел;
- итеративный поиск цели, отсутствующей в исходной таблице инициатора.

**Не входит в этапы 1–2** (добавляется на этапах 3–4): TLS/AKE,
`STORE`/`FIND_VALUE`, подписанные `NodeRecord`, туннели, прикладные
сервисы. Формат кадра версии 1 спроектирован так, чтобы эти функции
добавлялись без его изменения.

## 2. Модульная структура

```text
cmd/node/           точка входа: daemon, --lookup, --dump-tables
internal/
  transport/        TCP-сервер и клиент, пул соединений, кадрирование
  protocol/         константы версии и типов, payload-структуры, JSON-кодек
  identity/         Ed25519-ключ, вычисление NodeID
  routing/          XOR, Contact, k-bucket, RoutingTable
  rpc/              клиент RPC, корреляция по request_id, диспетчер
  node/             конфиг, bootstrap, lookup, обработчики, dump, signals
  logging/          обёртка над log/slog
scripts/            запуск и остановка стенда, сценарии экспериментов
configs/            по 21 yaml на каждую топологию (star, ring)
docs/               спецификация протокола, архитектура, результаты
testdata/           независимые тест-векторы
```

**Разделение обязанностей:**

- `transport` не знает про Kademlia, типы сообщений и семантику payload;
- `protocol` не знает про сеть, только про сериализацию;
- `routing` не знает про RPC — принимает callback `pinger func(*Contact) bool`;
- `rpc` не знает про Kademlia — маршрутизирует по `type`;
- `node` — единственный модуль, связывающий всё вместе.

Прикладные обработчики (`internal/node/handlers.go`) не читают байты из
TCP-сокета и не парсят заголовок кадра — это делает `transport.Decode`.

## 3. Ключевые инженерные решения

### 3.1. Транспорт: пул исходящих соединений

**Решение:** пул переиспользуемых исходящих TCP-соединений по адресу
`host:port` (`internal/transport/pool.go`). Для каждого нового соединения
запускается горутина `readLoop`, читающая кадры и передающая их либо в
`rpc.Client.Deliver` (если это ответ на ожидающий запрос), либо в
`rpc.Dispatcher.Dispatch`.

**Обоснование:**

- 100 кадров переменной длины из демонстрации 13.2.4 идут по одному
  соединению — это ближе к реальной нагрузке, чем dial-per-RPC;
- исходящие ответы приходят по тому же соединению, что упрощает
  корреляцию;
- при ошибке записи/чтения соединение эвиктится из пула и пересоздаётся
  при следующем `Get`.

**Альтернатива:** dial-per-RPC отвергнута из-за накладных расходов
`connect()` на каждый PING/lookup и риска исчерпания портов в сети из
21 узла.

### 3.2. Кадрирование: фиксированный заголовок 24 байта

**Решение:** бинарный формат с фиксированным заголовком 24 байта,
`payload_length` проверяется до выделения буфера.

**Обоснование:**

- TCP не сохраняет границы сообщений, поэтому кадрирование обязательно;
- `io.ReadFull` на заголовке и на payload корректно обрабатывает
  частичные чтения — «одно чтение — один кадр» не предполагается;
- проверка `payload_length > MAX_FRAME_PAYLOAD` **до** `make` защищает от
  аллокации памяти по запросу злоумышленника;
- `request_id` в заголовке — универсальный механизм корреляции запросов
  и ответов, применимый и на этапе 3 для AEAD.

### 3.3. Сериализация payload: JSON

**Решение:** JSON через `encoding/json` с `DisallowUnknownFields`.

**Обоснование** (сравнение в `PROTOCOL.md`, §5):

- payload этапов 1–2 мал (Contact + 1–3 поля);
- читаемость логов важнее компактности;
- отсутствие внешней схемы ускоряет итерации;
- возможность перейти на CBOR без изменения формата кадра, так как кодек
  изолирован в `internal/protocol/codec.go`.

### 3.4. Идентичность: Ed25519 и детерминированный NodeID

**Решение:**

```
NodeID = SHA-256("p2p:identity:ed25519:v1:" || raw_ed25519_pubkey)
```

**Обоснование:**

- Ed25519 — современный алгоритм подписи с проверенной реализацией в
  стандартной библиотеке Go;
- префикс `p2p:identity:ed25519:v1:` обеспечивает algorithm agility:
  при добавлении других схем подписи на этапе 3+ их `NodeID` не столкнутся
  с Ed25519;
- детерминированная связь `NodeID` ↔ публичный ключ позволяет любому узлу
  независимо проверить контакт (`DeriveNodeID(pub) == node_id`).

**Хранение ключа:** `state/<node>/identity.key`, права `0600` на файл и
`0700` на каталог. Закрытый ключ никогда не покидает каталог состояния.

### 3.5. k-bucket: 256 фиксированных bucket

**Решение:** 256 bucket по индексу старшего установленного бита
XOR-расстояния относительно локального `NodeID`.

**Обоснование:**

- детерминированное отображение `NodeID → bucket` без операций split/merge;
- проще тестировать: каждый контакт всегда попадает в один и тот же bucket;
- классическое динамическое разбиение даёт лучшее распределение при
  больших `N`, но для `N ≤ 21` разница несущественна;
- стандартный подход, используемый в учебных реализациях Kademlia.

**Порядок контактов:** LRU в голове, MRU в хвосте. При переполнении
выполняется **асинхронный** PING LRU-контакта; мьютекс таблицы отпускается
до сетевого вызова, чтобы избежать deadlock.

**Инварианты:**

- один `NodeID` присутствует не более одного раза;
- контакт с тем же `NodeID`, но иным публичным ключом — отклоняется;
- локальный `NodeID` не помещается в собственную таблицу;
- живой LRU-контакт не вытесняется без PING.

### 3.6. Итеративный lookup: α=3, K=4

**Решение:** параллельные запросы с `ALPHA = 3`, условие остановки
`lookupConverged`.

**Обоснование:**

- `ALPHA = 3` — стандарт Kademlia, компромисс между нагрузкой и временем
  поиска;
- условие остановки по «K-му ближайшему опрошенному» гарантирует, что
  дальнейший опрос не улучшит итоговый список;
- счётчик `iterations` считает только продуктивные итерации (те, где был
  хотя бы один RPC).

**Запрещено:** последовательный опрос, скрытая загрузка полного списка
узлов, признание lookup успешным только потому, что все узлы заранее
известны инициатору.

### 3.7. Bootstrap: две схемы

**Решение:** реализованы star и ring как **схемы начального подключения**.
В общей Docker bridge-сети или на localhost они не являются физическими
топологиями — все узлы IP-достижимы друг для друга.

**Star:**
```
   node-01 (seed)
     ^  ^  ^  ^  ^
     │  │  │  │  │  PING + self-lookup
   n-02 n-03 ... n-21
```

**Ring:**
```
  n-01 → n-02 → n-03 → ... → n-21
   bootstrap: node-XX подключается к node-(XX-1)
```

**Порядок запуска:** seed без bootstrap, затем остальные с интервалом
0.3 с (star) или 0.5 с (ring). Интервал в ring больше, чтобы каждый
предыдущий узел успел заполнить таблицу до прихода следующего.

После PING bootstrap-узла и добавления его в таблицу новый узел
выполняет `LookupNode(self)` для заполнения таблицы. После этого
bootstrap-узел не требуется для контрольных lookup.

### 3.8. Сохранение состояния

**Решение:** таблица маршрутизации выгружается в
`state/<node>/table.json` в двух случаях:

- сразу после завершения bootstrap (требование 22.2 п.6);
- по сигналу `SIGUSR1` — для снятия дампов во время эксперимента;
- при штатной остановке узла (`Wait` → `SaveTableDump`).

Запись выполняется через `.tmp` + `rename`, чтобы читатель никогда не
увидел половину файла.

## 4. Диаграмма потока сообщения

```
                  ┌──────────────────────────────────────┐
                  │           Node (orchestrator)        │
                  └──────────────┬───────────────────────┘
                                 │
              ┌──────────────────┼──────────────────┐
              ▼                  ▼                  ▼
    ┌──────────────┐    ┌───────────────┐    ┌──────────────┐
    │ transport    │    │  rpc.Client   │    │  routing     │
    │ TcpListener  │    │  waiters map  │    │  RoutingTable│
    │ Pool         │    │  Deliver()    │    │  k-buckets   │
    └──────┬───────┘    └───────┬───────┘    └──────┬───────┘
           │                    │                    │
           │ Decode/Encode      │ SendRequest        │ AddOrUpdate
           │                    │                    │ FindClosest
           ▼                    ▼                    ▼
    ┌────────────────────────────────────────────────────────┐
    │          rpc.Dispatcher.Dispatch(frame)                │
    │          handlers[type](ctx, frame) -> *Frame          │
    └────────────────────────────────────────────────────────┘
                            │
                            ▼
              ┌──────────────────────────┐
              │ node.HandlePing          │
              │ node.HandleFindNode      │
              └──────────────────────────┘
```

Кадр читается `transport.Conn.ReadFrame` → попадает в `readLoop` →
если это ответ на ожидающий RPC, уходит в `rpc.Client.Deliver` → иначе
в `rpc.Dispatcher.Dispatch` → вызывается `HandlePing` или
`HandleFindNode`, обновляющий таблицу.

## 5. Алгоритм bootstrap (детально)

```
1. New(cfg, logger)
   ├─ identity.LoadOrCreate(cfg.NodeStateDir)
   ├─ pool = transport.NewPool(connectTimeout)
   ├─ table = routing.New(nodeID, K, pingContact, logger)
   ├─ rpc   = rpc.NewClient(pool, logger)
   └─ dispatcher = rpc.NewDispatcher({PING: HandlePing,
                                      FIND_NODE: HandleFindNode})

2. Start()
   ├─ transport.NewServer(host, port, onConn)
   ├─ listenPort = srv.Addr().(*net.TCPAddr).Port    // важно при :0
   └─ go srv.Serve()

3. BootstrapPeers()
   └─ Bootstrap(cfg.BootstrapPeers)
      ├─ pingPeer(addr)                            // PING + валидация
      ├─ table.AddOrUpdate(peer)
      ├─ LookupNode(self)                           // self-lookup
      └─ SaveTableDump()                            // требование 22.2 п.6

4. Wait(ctx)
   ├─ SaveTableDump()                               // на shutdown
   └─ srv.Close()
```

`pingPeer` — обёртка над `rpc.SendRequest + contactFromWire +
table.AddOrUpdate`, реализующая требование 19.3.

## 6. Обработка ошибок и отказов

| Ситуация                             | Поведение                                       |
|--------------------------------------|-------------------------------------------------|
| Не удалось установить TCP-соединение | `WARN dial failed`, `ErrRPCTimeout`             |
| Тайм-аут `PONG`                      | LRU-контакт удаляется, новый добавляется        |
| Тайм-аут `FIND_NODE`                 | Кандидат фиксируется в `Timeouts`, не повторяется |
| Неверный `request_id` в ответе       | Ответ не сопоставляется ожидающему запросу      |
| Неверный `target_node_id` в ответе   | Ответ отклоняется (требование 20.2)             |
| Битый кадр от удалённой стороны      | Отправляется `ERROR`, соединение закрывается    |
| Ошибка сохранения таблицы            | `WARN`, работа узла продолжается                |
| Bootstrap-узел недоступен            | Переход к следующему peer из списка             |
| Все bootstrap-peer недоступны        | `ErrNoBootstrapReachable`, работа продолжается  |

Узел **не завершается** из-за ошибочного входящего кадра или недоступности
одного удалённого узла.

## 7. Конфигурация

Каждый узел принимает параметры из YAML-файла. Параметры, влияющие на
алгоритмы, вынесены в конфиг и не требуют правки кода:

| Параметр             | Назначение                                  |
|----------------------|---------------------------------------------|
| `NODE_STATE_DIR`     | Индивидуальный каталог состояния            |
| `LISTEN_HOST/PORT`   | Адрес TCP-сервера                           |
| `BOOTSTRAP_PEERS`    | Начальные контакты                          |
| `NODE_ID_BITS`       | Фиксировано 256                             |
| `K_BUCKET_SIZE`      | 4 для продвинутого уровня                   |
| `ALPHA`              | 3                                           |
| `CONNECT_TIMEOUT_MS` | Тайм-аут установления TCP                   |
| `READ_TIMEOUT_MS`    | Тайм-аут ожидания кадра                     |
| `PING_TIMEOUT_MS`    | Тайм-аут ответа PONG                        |
| `MAX_FRAME_PAYLOAD`  | 65536                                       |
| `PROTOCOL_VERSION`   | 1                                           |
| `LOG_LEVEL`          | DEBUG / INFO / WARN / ERROR                 |
| `ADVERTISE_HOST`     | Адрес, сообщаемый другим узлам              |

При `LISTEN_PORT = 0` ОС выдаёт свободный порт; фактический порт
сохраняется в `n.listenPort` и используется в `SelfContact` (важно для
тестов и demo.sh с эфемерными узлами).

## 8. Развёртывание

**Целевые платформы:** Zorin OS (разработка и эксперименты), любой Linux.

**Способ запуска:** независимые процессы на `127.0.0.1:9101..9121`.
Один бинарник `bin/node`, разные конфиги. Это упрощает отладку и даёт
корректную изоляцию состояния, порта, ключей и журнала.

**Docker/Compose** на этапе 2 не используется: 21 процесс на localhost
достаточно для проверки невырожденности DHT и сравнения bootstrap-схем.
Контейнеризация — часть этапа 4 при добавлении ограниченного underlay
(`docker networks`, `nftables`).

**Файловая структура запуска:**

```text
state/star/node-01/identity.key       // Ed25519 ключ
state/star/node-01/table.json          // дамп таблицы (SIGUSR1 / shutdown)
results/star/logs/node-01.log          // slog JSON
results/star/lookup/lookup-N.json      // результаты контрольных lookup
configs/star/node-01.yaml              // конфиг узла
```

## 9. Ограничения этапа 2

**Явно и важно.**

**Канал не защищён.** На этапах 1–2 отсутствуют TLS, AKE и
аутентификация транспортных сообщений. Публичный ключ передаётся в составе
`Contact` без подписи транспортного кадра. Это означает:

- этап 2 **не устраняет MITM-угрозу**;
- этап 2 **не обеспечивает конфиденциальность** payload;
- любой узел в underlay-сети может подменить `PONG` или
  `FIND_NODE_RESPONSE`, если знает чужой `NodeID` и адрес;
- защита от replay отсутствует.

Защищённая сессия на TLS 1.3 mTLS (упрощённый уровень) или собственном
AKE (продвинутый) появляется на этапе 3.

**Что уже защищено на этапе 2:**

- подмена `NodeID` без знания приватного ключа Ed25519 невозможна
  (проверка `SHA-256(pub) == node_id` при приёме контакта);
- контакт с тем же `NodeID`, но иным публичным ключом отклоняется;
- закрытые ключи не покидают каталог состояния (права `0600/0700`);
- `payload_length` проверяется до аллокации;
- нарушение протокола закрывает соединение.

**Ограничения DHT:**

- STORE/FIND_VALUE не реализованы — только маршрутизация;
- TTL и репликация записей отсутствуют;
- периодический refresh таблицы не реализован (только self-lookup при
  bootstrap).

**Ограничения адресации:**

- один TCP-адрес на контакт (нет IPv6, multiaddr, NAT traversal, relay);
- нет поддержки IPv6.

## 10. Результаты экспериментальной проверки

На сети из 21 узла на `127.0.0.1`, `K_BUCKET_SIZE = 4`, `ALPHA = 3`,
сравнены две bootstrap-схемы.

| Метрика                              | Star    | Ring    |
|--------------------------------------|--------:|--------:|
| Средний размер таблицы `avg_size`    | 9.33    | 9.90    |
| Максимальный размер                  | 13      | 14      |
| Минимальный размер                   | 5       | 6       |
| Узлов с размером < N-1 = 20          | 21/21   | 21/21   |
| Bootstrap прошли успешно             | 20/20   | 20/20   |
| Контрольных lookup успешных          | 10/10   | 10/10   |
| Lookup после отказа seed             | success | success |
| Диапазон итераций lookup             | 2–4     | 2–3     |
| Диапазон RPC на lookup               | 6-12    | 5–9     |

**Выводы:**

- обе схемы дают невырожденную DHT (`avg_size` далеко от `N-1 = 20`);
- ring даёт более **равномерное** заполнение (`min_size` 6 против 4) и
  более **стабильный** lookup (2–3 итерации против 2–5);
- в обеих схемах отказ bootstrap-узла не влияет на lookup между ранее
  присоединившимися узлами — bootstrap-граф отделён от DHT-overlay.

Сырые данные — в `docs/experiments/{star,ring}/`.

## 11. План этапа 3

Архитектура этапов 1–2 спроектирована так, чтобы следующие возможности
добавлялись без изменения базовой структуры:

- **подписанные `NodeRecord`** — поле в payload `FIND_VALUE_RESPONSE`;
  `NodeRecord` переиспользует Ed25519-подпись identity-ключа;
- **`STORE` / `FIND_VALUE`** — новые типы сообщений `0x05`–`0x08`,
  зарезервированные в `PROTOCOL.md`, §4;
- **TTL, репликация, republish** — надстройка над DHT-хранилищем,
  независимым от `routing.Table`;
- **TLS 1.3 mTLS или собственный AKE** — оборачивает `transport.Conn`,
  не меняя `rpc.Client` и `rpc.Dispatcher`;
- **туннели** — новые типы сообщений `TUNNEL_*`, отдельный модуль
  `internal/tunnel`;
- **прикладные сервисы** — `APP_MESSAGE`, `APP_ACK`.

Заголовок кадра версии 1 не меняется: новые типы вписываются в уже
зарезервированные коды `0x05–0x3F`. Поле `flags` (2 байта) начнёт
использоваться для признаков шифрования и фрагментации.
